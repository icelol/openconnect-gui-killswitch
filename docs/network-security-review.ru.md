# Аудит сетевой части и безопасности — 2 ноября 2026

Проверена реализация после v1.2.1 и русской документации: базовый коммит
`51d17ab`, ветка исправлений `audit/network-security`. Это анализ исходников
и локальные регрессионные проверки, а не сертификат отсутствия уязвимостей.
Исправления ветки ещё не входят в опубликованные установщики v1.2.1.

Практическая инструкция, схема, команды ON/OFF и восстановления:
[как работает kill switch](killswitch-operation.ru.md).

## Что проверялось

- macOS: генерация PF, порядок правил/разделов, принадлежность состояний,
  IPv4/IPv6, исключения DNS и шлюза, привязка utun, сохранение ON/OFF,
  повреждённые JSON, восстановление и права установленных компонентов.
- Windows: provider/sublayer WFP, постоянные блоки и динамические разрешения,
  транзакции, App ID/SYSTEM, проверка адаптера, DNS parser и TCP fallback,
  SCM, named pipe, проверка клиента/сервера, ACL и поиск DLL.
- Общее: допустимые команды IPC, границы сообщений, привязка ответов к запросу
  авторизации, повторный Connect, отмена, доступность OFF, закрытие GUI,
  обработка журнала, старые настройки паролей и ключей.
- Разработка: сборка с поставляемым patched OpenConnect 9.21, unit/UI-тесты,
  безопасный тест recovery-скрипта, статический анализ и мутации DNS parser.

На рабочем Mac выполнены только чтение состояния/диагностики службы и проверка
владельцев/прав каталогов. Переключение реального PF, обрыв текущей сети,
перезапуск установленной службы и отправка VPN-пароля для аудита не выполнялись.

## Подтверждённые ошибки и исправления

| Область | Ошибка и последствия | Исправление |
| --- | --- | --- |
| macOS OFF | Повреждение журнала восстановления останавливало OFF до очистки PF; некорректная загрузка могла частично менять поля в памяти | Загрузка применяется только после полной проверки; явный OFF очищает и проверяет свой раздел, сохраняет повреждённые файлы отдельно, записывает корректное OFF |
| macOS recovery | Ошибка `plutil` на повреждённом JSON могла прервать административный скрипт | Независимая очистка раздела, атомарная запись минимального OFF, карантин повреждённых файлов; неизвестный PF token не используется |
| Windows DNS | Повторы валидных TC-ответов запускали новые ожидания TCP, обходя общий срок запроса; это задерживало OFF и продлевало DNS-исключение | Общий бюджет для всех ожиданий и чтения очереди; максимум один TCP fallback на запрос; ограниченный буфер |
| Незавершённый вход | После закрытия владельца GUI попытка могла продолжаться между запросами пароля или при подготовке туннеля | Отмена любой ещё не установленной сессии владельца; уже установленный VPN сохраняется |
| Канал управления VPN | Унаследованный код делал producer command pipe блокирующим; заполнение могло подвесить поток управления службой и OFF | Неблокирующий контракт libOpenConnect сохранён; запросы статистики/отмены объединяются, отмена повторяется асинхронно, устаревший дескриптор отвязывается до закрытия |
| Старый редактор профиля | Предлагал вводить OTP-секреты/ключи и настройки, которые системная служба не использует; на macOS старое хранилище не шифрует их | Неподдерживаемые элементы скрыты/отключены; сохранение служебного профиля не записывает новые секреты и не переписывает старые данные |

Это прежде всего исправления доступности управления и обращения с данными.
Получение произвольного root/SYSTEM через проверенные команды IPC в ходе
проверки не подтверждено. Неизвестные уязвимости это не исключает.

Старые секреты из прежних версий **не удаляются автоматически**. На macOS
`CryptData` исторически возвращает исходные байты; в Windows использует DPAPI,
но у старого кода есть fallback без шифрования при недоступной библиотеке.
Не следует считать все исторические настройки зашифрованным хранилищем.
Явное удаление ненужного профиля/полная очистка убирает активные настройки;
копии в резервных системах требуют отдельного решения. Текущая служба
не сохраняет пароль входа или cookie авторизации.

## Почему OFF не должен отключать PF/BFE целиком

Защита принадлежит приложению, а PF/BFE используются всей системой.
Правильный OFF проверяет отсутствие **собственных** фильтров и сохраняет
намерение OFF. Общий PF может остаться включённым из-за других владельцев.
Чужие правила по-прежнему могут запрещать доступ. Ни `pfctl -d`, ни
`netsh advfirewall reset`, ни остановка BFE не являются штатным восстановлением.

При неизвестном PF token безопаснее оставить ссылку включения PF и убрать
собственный блок, чем угадывать token и затрагивать другой продукт.

## Что остаётся границей безопасности

1. **Ранняя загрузка.** Автозапуск службы не доказывает нулевую утечку до её
   запуска/восстановления PF либо загрузки фильтров BFE. Для строгого корпоративного
   требования нужен отдельный проект загрузочной сетевой политики и внешнее
   наблюдение трафика при старте.
2. **Локальный пользователь и администратор.** Выбранная учётная запись сейчас
   имеет право OFF; другие её процессы могут отправлять такие же команды.
   Root/SYSTEM, администратор и драйвер ядра не входят в модель противника.
   Пароль на выключение должен проверяться службой, а не только GUI.
3. **macOS исключения root.** PF ограничивает шлюз адресом/портом и UID 0,
   но не отдельным executable. Временное разрешение DNS также относится к root.
   Windows дополнительно проверяет App ID процесса и SYSTEM SID.
4. **Мосты/виртуальные машины.** Транзитный, bridged/forwarded трафик нельзя
   считать покрытым проверкой обычных приложений ноутбука.
5. **Локальная доступность IPC.** Windows pipe проверяет пользователя на каждом
   сообщении, однако подключения до проверки могут занимать ограниченные слоты.
   SID-ограниченный DACL уменьшит возможность локального отказа в обслуживании.
6. **Сложные ACL.** Проверка файлов Windows ориентируется на обычные разрешающие
   ACE, которые создаёт установщик. Расширение поддержки нестандартных ACL
   должно отклонять непонятные разрешающие типы, а не игнорировать их.
7. **Подпись и доверие к поставке.** Текущие EXE/PKG без подписи издателя,
   macOS ad-hoc без notarization. Контрольная сумма обнаруживает изменение файла,
   но не заменяет удостоверенную подпись доверенного издателя.
8. **Привилегированный parser.** VPN-протоколы и конфигурация сервера обрабатываются
   в root/SYSTEM-процессе. Нужно регулярно обновлять libOpenConnect/TLS/XML и
   сокращать полномочия этих обработчиков, где это технически возможно.

## Зависимости и известные advisories

В проверенном Windows-пакете v1.2.1 манифест указывает OpenConnect 9.21,
GnuTLS 3.8.13-3, Qt Base 6.12.0-1 и libxml2 2.15.4-3.
OpenConnect 9.21 соответствует последней версии на проверенной официальной
[странице загрузки](https://www.infradead.org/openconnect/download.html).
GnuTLS 3.8.13 включает исправления перечисленных на официальной странице
[advisories](https://www.gnutls.org/security-new.html) от 29 апреля 2026 года.
Это не утверждение, что все зависимости не имеют других уязвимостей.

В [списке Qt](https://wiki.qt.io/List_of_known_vulnerabilities_in_Qt_products)
указаны в том числе проблемы Qt 6.12.0, исправленные в 6.12.1, например
CBOR-to-JSON и XML Qt5Compat. В просмотренных исходниках нет обработки
недоверенного CBOR или использования Qt5Compat; применимость этих двух путей
к клиенту не подтверждена. Тем не менее следующий выпуск следует собирать с
исправленной Qt либо подтверждёнными backport-патчами, с повторным аудитом
**фактически упакованных** библиотек. Номер версии без проверки пакетных патчей
недостаточен для заключения о конкретной CVE.

Полный непрерывный мониторинг CVE всех транзитивных библиотек этим аудитом
не реализован. Следующий шаг — SBOM из установленного пакета и регулярная
проверка применимости официальных advisories.

## Проверки и воспроизведение

Локальный результат: все 4 набора CTest прошли. Внутри Qt-наборов (включая
инициализацию/завершение QtTest): DNS 11 PASS, PF 34 PASS, GUI/служба 26 PASS;
отдельно 5 сценариев recovery-скрипта. Для повреждённого состояния PF и
блокирующего command pipe новые проверки также запущены против старой
реализации и воспроизвели исходные ошибки.

Clang Static Analyzer просмотрел 8 ключевых файлов. Два предупреждения в
`NetworkService.cpp` разобраны вручную: обработчик timer имеет живой QObject
context, а `QFutureWatcher` принадлежит QObject и удаляется через `deleteLater`.
Подтверждения null-this/leak по этим двум сообщениям не получено; модель
Qt в анализаторе неполна. Статический анализ не заменяет динамические проверки.

Сборка и штатный набор проверок:

```sh
python3 scripts/validate-release.py
cmake --build build-audit -j 6
ctest --test-dir build-audit --output-on-failure
git diff --check
```

Каталог `build-audit` предварительно настраивается CMake с patched библиотекой
из `scripts/build-openconnect.sh`, как описано в [сборке релиза](release.md).
Сборка против случайной системной OpenConnect не проверяет её API совместимости.

Регрессионные сценарии используют внедрённые PF/сеансы и локальные DNS fixtures
на loopback со случайными портами; рабочий VPN не требуется. Отдельный тест
`recovery_script_test.py` копирует recovery-скрипт в sandbox и подменяет все
вызовы PF/launchd/killall заглушками до исполнения. Он не получает sudo.

Для поиска ошибок parser добавлен `tests/fuzz_dns_response.cpp`: libFuzzer
без сети, с максимальным входом 8192 байта. Пример в окружении с Qt/pkg-config
и Clang с установленным runtime libFuzzer:

```sh
clang++ -std=c++17 -g -O1 -fsanitize=fuzzer,address,undefined \
  -fno-omit-frame-pointer -Isrc tests/fuzz_dns_response.cpp \
  src/WindowsDnsBootstrap.cpp $(pkg-config --cflags --libs Qt6Core Qt6Network) \
  -o /tmp/ocgui-dns-fuzz
/tmp/ocgui-dns-fuzz -runs=150000 -max_len=8192
```

В Apple Command Line Tools на проверенном Mac runtime libFuzzer отсутствует.
Кроме того, установленный ASan runtime Apple Clang 17 на этом Mac зависает
при инициализации до входа в `main` (проверено по stack sample). Это ограничение
инструментария, а не пройденная проверка памяти. Выполнен ограниченный
воспроизводимый тест мутаций под **UBSan**:

```sh
clang++ -std=c++17 -g -O1 -DOCGUI_FUZZ_STANDALONE \
  -fsanitize=undefined -fno-sanitize-recover=all -fno-omit-frame-pointer -Isrc \
  tests/fuzz_dns_response.cpp src/WindowsDnsBootstrap.cpp \
  $(pkg-config --cflags --libs Qt6Core Qt6Network) -o /tmp/ocgui-dns-mutations
/tmp/ocgui-dns-mutations
```

На этом Mac 150 000 мутаций завершились без сообщения UBSan. ASan и
coverage-guided libFuzzer остаются непроверенными. Этот режим он не даёт coverage feedback, не заменяет
долгий fuzzing и не инструментирует уже собранные библиотеки Qt.

Нативная сборка Windows и live WFP smoke новой ветки прошли в
[CI 41449571079](https://github.com/icelol/openconnect-gui-killswitch/actions/runs/41449571079)
для исходников `5fe1942` (тестировался синтетический merge-коммит PR `facd613`).
Подтверждены IPv4/UDP, блокировка открытого TCP, DNS при ON, Connect/Cancel,
локальный вход TLS/CSTP с передачей UDP через Wintun, сохранение ON после
перезапуска/обновления, отказ обновления/удаления при открытом GUI,
административное восстановление, явный OFF и сохранение чужого правила.
Внешний IPv6 на runner недоступен: сетевая проверка IPv6 не считается пройденной.
Реальные Windows 10/11, сон/смена сети/ранняя загрузка и полный прогон рабочего
VPN с новой веткой остаются непроверенными. Новый EXE собран в CI, но
опубликованные установщики v1.2.1 этим аудитом не заменяются.
